# Mobile frontend: source of truth

This is the canonical guide for people and coding agents working in
`frontend-mobile/`. It replaces the previous architecture, offline-tournament,
and Android-system-settings notes. Keep this document current when a change
affects these contracts.

## Project structure

- `app/` contains Expo Router route definitions only.
- `src/providers/` composes app-wide providers. Do not add `src/app/`: Expo
  Router would interpret it as a route root.
- `src/features/<feature>/screens/` holds complete screens;
  `components/`, `hooks/`, and `services/` hold feature-local UI, effects, and
  API/persistence code respectively.
- `src/components/` is for components shared by multiple features.
- `src/types/`, `src/constants/`, `src/utils/`, and `src/styles/` contain
  shared primitives and visual properties.
- `src/system/` owns global system-UI behavior.

Move existing behavior before changing it: preserve API paths, validation,
messages, delays, styles, and public component props during refactors.

## Local-first tournament contract

Ongoing tournaments must work without a network connection. The device is the
immediate source of UI state; the backend is the durable, shared authority once
synchronization is possible.

1. On the first open, download one complete snapshot: event, registrations,
   player rosters, groups, bracket, results, and server revision. Persist it in
   `AsyncStorage`. Do not retain past tournaments in the offline cache.
2. Render the cached snapshot immediately. When online, request only
   `tournament-state/revision`; download a full snapshot only if its revision
   changed.
3. Every tournament action first runs locally through a pure transition in
   `src/features/organizations/services/tournamentEngine.ts`, then persists
   the resulting state and an **intent-level semantic operation** to the queue.
   The UI must never call the backend to calculate draws, standings,
   qualification, bracket progression, or results.
4. The queue is sent after each local change, on foregrounding, and periodically
   while work remains. A network failure must never roll back local state.
5. The backend atomically accepts the client-calculated snapshot only when
   `base_revision` matches, then increments the revision.
6. On a revision conflict, fetch the latest snapshot, replay queued semantic
   operations with the same engine, persist the rebased result, and retry. This
   allows compatible edits from separate organizers to merge.

For a new tournament format, add deterministic match IDs plus a new operation
and transition to `tournamentEngine.ts`; extend backend snapshot validation and
persistence in `backend/app/api/routes/tournament_sync.py`.

## Large data-feed caching and versions

For a screen that displays a larger, reusable payload (for example a list of
tournaments, teams, registrations, results, or a dashboard feed), use a
versioned offline cache instead of repeatedly downloading the complete data.

1. Persist the last successful full payload together with its server version.
2. When re-entering the relevant screen, request only a small version endpoint.
3. If the version is unchanged, render the cached payload and do not request
   the full endpoint. If it changed, download and persist the new full payload.
4. If the network is unavailable, keep rendering the last cached payload.
5. Do not use time-based polling for these feeds unless the product explicitly
   requires live updates. Refresh is driven by entering the screen or an
   explicit user action.

Do not add this mechanism to tiny or transient responses such as a single
number, a simple boolean, a one-off form action, or a small detail lookup. The
extra version request is justified only when it avoids repeatedly transferring
a materially larger payload.

## Android and Expo rules

- `app.json` is the source for Expo/Android build settings; `app.config.ts`
  enforces that production API URLs use HTTPS; `eas.json` selects `APP_ENV`.
- `android/` is generated by Expo prebuild and is not committed. Do not make
  manual changes there; regenerate and rebuild after native configuration
  changes.
- The app keeps status and navigation UI OS-managed and visible. `app.json` and
  `src/system/SystemUiController.tsx` must agree. Use safe-area-aware layouts,
  `edgeToEdgeEnabled: true`, flexible orientation, and resize mode for the
  keyboard.
- `expo-keep-awake` is intentionally excluded from native autolinking. Expo
  attempts to use it only in development to prevent screen sleep; on some
  Android activity transitions it can reject with `Unable to activate keep
  awake`. The app does not need that development-only behavior.
- Release builds must not permit cleartext HTTP. `allowBackup` remains disabled
  and unneeded storage, overlay, and vibration permissions remain blocked.

## Local event-form assistant

- `src/features/localAi/` owns model download state, local inference, speech UI,
  the shared screen/capability manifest, and constrained action-plan contracts.
- The selected model is Google's Gemma 4 E2B Instruct Q4_0 GGUF. Download the
  pinned model revision into the app document directory; do not bundle its
  multi-gigabyte weights in the application package.
- Speech recognition produces text only. Gemma receives that text plus the
  current screen manifest, form state, option vocabulary, constraints, and
  recent session turns. It may return only a schema-constrained action plan;
  the app validates and grounds every action against the live UI before
  applying it. The assistant must never submit or create the event.
- `llama.rn` and `expo-speech-recognition` are native modules. Any related
  config or dependency change requires a fresh development build; Expo Go and
  a Metro-only reload are not sufficient.

## Development and verification

Install and run with `npm install` and `npm run start`. For Android emulator,
set `EXPO_PUBLIC_API_BASE_URL=http://10.0.2.2:8000`; for a physical device use
the computer's reachable LAN address, never `localhost`.

After a structural or native-config change run `npm run typecheck` and
`npm run bundle:android`. A native Android config change also requires a fresh
development build (`npx expo run:android`); Metro reload alone is insufficient.
